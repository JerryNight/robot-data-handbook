## 两条路线的对比

这一章讲的三个数据集，代表了三种不同的解题思路。放在一起看最清楚：

| | OXE | DROID | 你自采 |
|---|---|---|---|
| 解决什么 | 格式不统一 | 场景不够多样 | 能不能用 |
| 手段 | 转换 60 个已有数据集 | 统一硬件 + 分散场景 | 自己定 schema |
| 本体多样性 | 22 种（实际训练 9 种） | 1 种 | 1 种 |
| 场景多样性 | 一般（多为实验室桌面） | **强**（564 场景 / 52 建筑） | 取决于预算 |
| 主要代价 | 动作空间投影丢信息 | 人力成本极高 | 缺陷无声 |

**关键判断：多样性来自哪里，就在哪里投入。** OXE 选择统一格式，因为它要的是本体多样性；DROID 选择统一硬件，因为它要的是场景多样性。这两件事是正交的，别指望一个方案同时给你。

## 阅读这些数据集时要问的五个问题

不管看哪个数据集，先回答这五个问题，就能判断它适不适合你：

1. **动作空间是什么？** 关节位置、末端增量、还是离散 token
2. **频率是多少？** 训练时的控制频率必须和数据一致——不在字段里就不可靠
3. **有没有成败标注？** 没有的话只能做纯 BC，无法做筛选
4. **语言指令是人工写的还是模板生成的？** 模板生成的多样性极差
5. **标定信息在不在包里？** 不在的话跨本体复用基本无望

## 常见错误清单

- 以为"聚合多个数据集"就等于"数据变多、效果变好"，忽略动作空间投影的损失
- 把控制频率写在 README 里而不写进数据字段
- 按平均位形定动作精度，忽略奇异位形下的放大
- 以为采集的瓶颈是存储——实际是人在场景里的时间
- 用"总 episode 数"衡量数据规模，不看场景和任务的覆盖
- 只留成功样本，丢掉筛选能力和最有信息量的边界情况
- 采完才想起标定，而不是采之前
- 拿慢动作数据做帧对齐校验，然后得出"数据没问题"的结论
