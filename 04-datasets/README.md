# 04 · 公开数据集

> 自己从零采数据之前，先看清楚别人踩过哪些坑。这一章的价值在于**避免重复投入**。

| # | 文章 | 一句话结论 |
|---|---|---|
| 1 | [多本体聚合](open-x-embodiment.md) | 22 个本体的数据在库里，训练只用得了 9 个——7 维动作装不下双臂，也装不下同一段末端轨迹的两种关节解 |
| 2 | [DROID](droid.md) | 每 288 小时人力产出 1 小时数据，其中 96% 以上的时间花在场景上，而不是采数据 |
| 3 | [自采数据](self-collected.md) | 缺陷不报错，只改含义；七项检查互不替代，而每一项都有它的失效下限 |

每篇都配一个零依赖的可运行实验，在 [`examples/04_datasets/`](../examples/04_datasets/)。所有数字都来自实际计算或公开论文，来源标注在文中。

## 三条路线的对比

这一章讲的三个数据集，代表三种不同的解题思路。放在一起看最清楚：

| | OXE | DROID | 你自采 |
|---|---|---|---|
| 解决什么 | 格式不统一 | 场景不够多样 | 能不能用 |
| 手段 | 转换 60 个已有数据集 | 统一硬件 + 分散场景 | 自己定 schema |
| 本体多样性 | 22 种（实际训练 9 种） | 1 种 | 1 种 |
| 场景多样性 | 一般（多为实验室桌面） | **强**（564 场景 / 52 栋建筑） | 取决于预算 |
| 主要代价 | 动作空间投影丢信息 | 人力成本极高 | 缺陷无声 |
| 可量化的代价 | 零空间 11%–34%；1 mm 量化在奇异位形放大 160 倍 | 有效率 0.35%；每场景 179 人时 | 可检测下限 0.2 rad |

**关键判断：多样性来自哪里，就在哪里投入。** OXE 选择统一格式，因为它要的是本体多样性；DROID 选择统一硬件，因为它要的是场景多样性。这两件事是正交的，别指望一个方案同时给你。

而你自己采的时候，两件事都不占：本体只有一种、场景只有几个，所以唯一的护城河是**数据质量**——这也是第三篇存在的理由。

## 阅读这些数据集时要问的五个问题

不管看哪个数据集，先回答这五个问题，就能判断它适不适合你：

1. **动作空间是什么？** 关节位置、末端增量、还是离散 token。是末端增量的话，问清楚是哪个坐标系下的
2. **频率是多少，写在字段里吗？** 训练时的控制频率必须和数据一致——不在字段里就不可靠
3. **有没有成败标注？** 没有的话只能做纯 BC，无法做筛选；全成功的数据集等于没有这个字段
4. **语言指令是人工写的还是模板生成的？** 模板生成的多样性极差
5. **标定信息在不在包里？** 不在的话跨本体复用基本无望，而且事后补不回来

## 常见错误清单

- 以为"聚合多个数据集"就等于"数据变多、效果变好"，忽略动作空间投影的损失
- 把控制频率写在 README 里而不写进数据字段
- 按平均位形定动作精度，忽略奇异位形下 160 倍的放大
- 以为采集的瓶颈是存储——实际是人在场景里的时间，一块硬盘装得下 350 小时
- 用"总 episode 数"衡量数据规模，不看场景和任务的覆盖；覆盖率还要看是不是按频率加权的
- 采集计划按 episode 排，不按场景排，于是大家挤在最近的几个场景里猛采
- 只留成功样本，丢掉筛选能力和最有信息量的边界情况
- 采完才想起标定，而不是采之前——而且把未去畸变的原图丢了
- 拿慢动作数据做帧对齐校验，然后得出"数据没问题"的结论
- 一致性检查只报一个数字（全身 offset），不看逐关节
