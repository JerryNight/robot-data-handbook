# 机器人系统五层栈

> 阶段 0 · 心智模型 ｜ 写作时间 2026-11
>
> 前置：[`what-is-robot-data.md`](what-is-robot-data.md)

## 1. 它解决什么问题

新手看机器人，容易以为它是"一个跑着 AI 模型的程序"，顶多再加点硬件。

实际完全不是。一台机器人在跑的时候，**五层异构系统在同时工作，各自有不同的时钟、不同的频率、不同的失败模式**。你收到的一批数据里，每个字段都来自其中某一层，带着那一层特有的误差。

不知道数据从哪一层来，就没法判断它能怎么用。这是数据平台设计时最容易被跳过、又最贵的一步。

举三个真实的问题：

- 为什么同一批数据里，图像和关节角差了 40 ms？—— 层的边界处有延迟
- 为什么动作标签看起来"平滑得不真实"？—— 你记录的是指令，不是执行结果
- 为什么换一台同型号机器人，数据就不能混用？—— 标定在 L1，不在模型里

这三个问题，都只能靠分层视角回答。

## 2. 五层栈

```
┌─────────────────────────────────────────┐
│ L4  学习层    策略网络 / VLA / 训练推理   │  1–10 Hz
├─────────────────────────────────────────┤
│ L3  算法层    感知 / 规划 / 控制          │  1–1000 Hz
├─────────────────────────────────────────┤
│ L2  中间件层  ROS 2 / DDS / TF2 / 录制    │  继承下层
├─────────────────────────────────────────┤
│ L1  驱动层    电机驱动 / 固件 / 总线 / SDK │  1–10 kHz
├─────────────────────────────────────────┤
│ L0  物理层    电机 / 减速器 / 传感器 / 结构│  微秒级电信号
└─────────────────────────────────────────┘
```

### L0 物理层

**有什么**：电机、减速器、编码器、相机、IMU、力/力矩传感器、连杆结构。

**这一层不产生数据，产生的是误差源。** 数据平台的人通常不看这层，但它决定了数据的质量上限：

- **机械回差**：齿轮间隙导致"指令角度"和"实际角度"有 0.1–1° 的偏差
- **传感器噪声**：IMU 的零偏随温度漂移，相机在低光下的噪声模型完全不同于白天
- **结构柔性**：重载时连杆会形变，末端实际位置偏离运动学算出来的位置

**结论**：任何"精确到小数点后四位"的动作标签，都要先想想 L0 允不允许这个精度。

### L1 驱动层

**有什么**：伺服驱动器、电机固件、现场总线（CAN / EtherCAT / RS485）、相机 SDK。

**输入 / 输出**：接收位置/速度/力矩指令（物理单位）→ 驱动电机 → 回报编码器读数、电流、温度。

**频率**：伺服环通常 **1–10 kHz**。这是整个栈里最快的闭环。

**这一层是时间戳的源头。** 这一点极其重要：

| 时间戳来源 | 精度 | 后果 |
|---|---|---|
| 硬件时间戳（驱动/FPGA 打） | 微秒级 | 可以精确对齐 |
| 驱动层软件时间戳 | 0.1–1 ms | 可用，需补偿传输延迟 |
| 上层收到时才打戳 | 1–10 ms，有抖动 | **多传感器对齐会出现系统性错位** |

如果你的数据里只有上层时间戳，那么"图像和力矩对齐"这件事从根上就做不到精确，只能估计。**这是选硬件时要问清楚的第一个问题**。

### L2 中间件层

**有什么**：ROS 2（底层 DDS）、TF2 坐标变换、launch 配置、bag 录制。

**输入 / 输出**：把各节点的数据流标准化成"带时间戳的话题"，并负责分发、录制。

**这一层是数据平台真正对接的层。** 你拿到的 rosbag 就是这一层的产物，它包含的结构信息（消息类型、QoS、时钟域）全部由这层决定。

三个必须知道的细节：

1. **消息类型即 Schema**。`sensor_msgs/msg/Image` 和自定义的 `MyRobot/msg/State` 是两套完全不同的东西，前者有社区共识，后者只有作者自己懂。
2. **QoS 会静默丢数据**。可靠性策略配成 `BEST_EFFORT` 时，队列满了直接丢帧，**不会有任何报错**。录制出来的数据"看起来完整"，实际缺帧。
3. **时钟域可能不止一个**。`use_sim_time` 打开时，节点用仿真时钟；关掉时用系统时钟。混用会导致时间戳跳变，肉眼看不出来。

### L3 算法层

**有什么**：感知（SLAM、目标检测、位姿估计）、规划（运动规划、轨迹生成）、控制（PID、阻抗控制、MPC、全身控制）。

**频率分布很宽**：

- 全局规划：**0.1–1 Hz**（算一次路径用几秒）
- 局部规划 / 轨迹生成：**10–100 Hz**
- 底层控制：**100–1000 Hz**

**这一层是"传统机器人"和"学习方法"的分界线。** 传统栈是模块化流水线，每层独立可调可查；端到端学习（包括 VLA）做的事，是用一个网络替代 L3 的大部分。

理解这一点对读论文很关键：**VLA 不是在"控制机器人"，它是在替代整条感知-规划-控制流水线**。所以它的输出必须包含足够的信息量，这也是为什么动作表示（见 [05/action-representation](../05-learning-from-data/)）这么难搞。

### L4 学习层

**有什么**：策略网络、VLA、训练与推理管线。

**输入**：观测（图像 + 本体状态），可能带语言指令。
**输出**：动作序列（通常是未来 K 步的动作块，即 action chunk）。

**频率：1–10 Hz。** 比其他层慢一到两个数量级，原因很实际：

| 模型规模 | 单次推理耗时 | 实际控制频率 |
|---|---|---|
| ACT 类小模型（~80M） | 10–30 ms | 30–50 Hz |
| 7B VLA（OpenVLA 级） | 100–300 ms | 3–10 Hz |
| 动作分块（K=50, 30Hz 数据） | 推理一次管 1.6 秒 | 可降到 1 Hz 以下 |

**动作分块就是为了掩盖这个速度差而发明的**：一次算出未来一段动作，慢慢执行，期间不推理。代价是反应变慢、无法应对突发变化。

**这一层的数据需求，反过来定义了 L1–L3 该怎么记录。** 比如：模型要吃 30 Hz 的动作，那录制时控制指令的频率必须 ≥30 Hz，否则只能插值——而插值会抹掉真实的动力学特性。

## 3. 数据在哪一层产生，带什么时间语义

这张表是本文最该记住的部分：

| 层 | 产生的数据 | 真实频率 | 时间戳来源 | 数据平台的关注点 |
|---|---|---|---|---|
| L0 | （无数据结构，只有物理量） | — | — | 噪声模型、精度上限 |
| L1 | 编码器原始值、电流、温度 | 1–10 kHz | **硬件或固件** | 时间戳精度、单位换算 |
| L2 | 标准化话题流、TF 树、bag | 继承下层 | DDS 接收时刻 | Schema、QoS 丢帧、时钟域 |
| L3 | 轨迹、控制指令、规划状态 | 0.1–1000 Hz | 节点内打戳 | 指令 vs 实际执行的差异 |
| L4 | 动作块、置信度、中间特征 | 1–10 Hz | 推理完成时刻 | 与观测的时间对应关系 |

## 4. 一个具体例子：抓杯子那 30 秒，五层在干什么

把抽象的时间线摊开，你会看到数据平台要面对的真实困难。

```
t=0.000s   L4  策略开始推理（输入：t=-0.033 那一刻的图像）
t=0.120s  L4  推理完成，输出未来 50 步动作块
t=0.120s  L3  动作块第一条下发给控制器
t=0.125s  L2  指令经 DDS 到达驱动节点（传输 + 序列化）
t=0.126s  L1  伺服环收到目标位置，开始执行
t=0.128s  L0  电机实际开始动（有机械延迟）
...
t=0.150s  L2  相机采集下一帧（曝光 + 读出 + 传输 ≈ 20 ms）
```

**关键延迟：从"图像被拍下"到"机器人真的开始动"，中间有 150–200 ms。**

这意味着：如果你在数据里把 `t=0.150` 的观测和 `t=0.120` 的动作配成一对，训练出来的策略会学到一个**系统性提前量**的动作。在真机上执行时，这个偏移会叠加真实延迟，表现为"总是慢半拍"或"过冲"。

工业界的常见做法（按精度从低到高）：

1. 不管延迟，直接按最近邻配对 —— 能跑，性能打折
2. 固定延迟补偿（减去一个常数）—— 简单，但延迟随负载变化时不准
3. 记录指令下发和执行确认两个时间戳，训练时按实际执行对齐 —— 需要 L1 配合
4. 硬件同步（PTP / 触发线），所有传感器共用一个时钟 —— 最好的方案，成本最高

**第 4 种方案的成本，就是"机器人数据平台"这个产品的真正技术门槛之一。**

## 5. 和数据平台有什么关系

四条结论：

1. **优先确认时间戳的源头在哪一层。** 只有 L1 的硬件时间戳才值得为"精确对齐"做投入，L2 的软件时间戳决定了你能做到的上限——先问清楚，再设计。
2. **"指令"和"执行"是两个不同的量，都要记。** 只记指令的数据集，在需要力控或高精度任务的场景下会直接不可用。
3. **QoS 丢帧是隐形杀手。** 平台必须在入库时做完整性校验（按时间戳算实际间隔，检测缺帧），不能信任"录制成功"这个状态。
4. **L4 的推理延迟是数据结构的一部分。** 数据集应该记录"策略推理耗时"这类元数据，否则训练时无法解释某些行为异常。
