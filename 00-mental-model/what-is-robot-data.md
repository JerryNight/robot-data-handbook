# 机器人数据到底是什么

> 阶段 0 · 心智模型 ｜ 写作时间 2026-11

## 1. 它解决什么问题

做数据平台的人接手机器人项目，第一反应通常是"不就是些视频和数值吗，转成 Parquet 进数据湖就行"。

这个判断会在两周内崩掉。因为机器人数据不是"一些文件"，而是**一个带时间轴的、多频率的、闭环反馈的物理过程记录**。用对象存储的思维去装它，会同时遇到四个问题：存不下、对不齐、看不懂、用不了。

所以在动手之前，得先回答一个比技术选型更早的问题：**机器人产生的数据，本质上是什么东西？**

## 2. 四种基本形态

任何一段机器人数据，拆开都是这四类东西的组合。

### Observation（观测）—— 机器人"看到"的

策略的输入。典型构成：

| 模态 | 典型频率 | 数据形状 | 备注 |
|---|---|---|---|
| RGB 相机 | 10–30 Hz | `H×W×3` uint8 | 通常 2–3 路（腕部 + 全局 + 侧视） |
| 深度图 | 10–30 Hz | `H×W` float32/uint16 | 与 RGB 需对齐 |
| 本体状态 | 50–500 Hz | 向量，7–30 维 | 关节角、关节速度、夹爪开合 |
| IMU | 100–1000 Hz | 六维向量 | 主要给移动底盘和人形 |
| 力/力矩 | 500–1000 Hz | 六维向量 | 装配、插拔类任务必需 |

关键点：**这些模态频率差两个数量级**。相机 30 Hz，力矩 1 kHz。你想把"某一时刻的观测"喂给模型，必须先回答"30 Hz 的那一帧，对应 1 kHz 里的哪 33 个采样点"。这是数据平台第一个真正的工程问题。

### Action（动作）—— 机器人"做"的

策略的输出，也是数据里最容易被低估的部分。

动作向量的维度和含义**完全取决于本体和控制接口**：

```
7-DoF 机械臂末端增量控制:  [dx, dy, dz, droll, dpitch, dyaw, gripper]   # 7 维
7-DoF 机械臂关节位置控制:  [q1, q2, q3, q4, q5, q6, q7, gripper]        # 8 维
双臂 ALOHA:                [14 个关节 + 2 个夹爪]                        # 16 维
人形 GR00T 类:             30+ 维（双腿 + 双臂 + 腰 + 手）
```

同样是"抓杯子"，不同机器的 action 向量维度、量纲、坐标系都不一样。**这就是跨本体数据无法直接合并的根本原因**——不是格式问题，是语义问题。

### State（状态）—— 容易被混淆的一个

严格说 state 是环境的真实状态，observation 是策略能看到的部分。实际工程里两者经常混用，尤其在仿真里"全状态"和"观测"是分开的：仿真可以给你所有物体的精确位姿（privileged state），真机只能给你像素。

这个区分在训练时很重要：**用 privileged state 训的策略，在真机上跑不起来**。

### Metadata（元数据）—— 决定数据能不能被用

没有元数据的机器人数据基本等于垃圾。必须包含：

- **时间戳**：每条记录的时间，以及它属于哪个时钟域（系统时钟 / 传感器时钟 / ROS 时间）
- **标定信息**：相机内参、相机到本体的外参、手眼标定结果
- **任务描述**：这段数据在干什么（自然语言指令，VLA 训练必需）
- **本体标识**：什么机器、什么末端、什么传感器配置
- **采集条件**：谁采的、什么时间、成功还是失败

少任何一项，这批数据在半年后就没法用了——因为你自己也说不清它当时是什么状态。

## 3. 和互联网数据的五个本质差异

这是软件工程背景的人最需要校准的部分。

### ① 频率不一致，必须先对齐

互联网数据天然是"一条一条"的。机器人数据是"多路并行流水"，各流频率不同。所有下游处理（训练、可视化、标注）都建立在"对齐后"的数据上。对齐做错，后面全错，且很难发现。

### ② 数据是闭环产生的

这是最反直觉的一点。

普通数据集是静态的：你采集一批图片，模型怎么学都不影响数据集。但机器人数据是**策略自己产生的**：模型在当前分布下犯错，就会把机器人带到训练集里没有的状态，然后在那里采集出更没见过的数据。

这叫 covariate shift，也是行为克隆（BC）失败的主因。**所以"数据量"在机器人领域不等于"数据覆盖"**，反复采同一类成功演示，边际收益会迅速归零。

### ③ 采集成本极高，没有 Crawl

互联网数据有爬虫，机器人数据只有人和机器。一段 30 秒的有效演示，需要：布置场景（几分钟）、遥操作（30 秒）、重置场景（几分钟）、检查质量（一遍）。

工业界大致量级：一条高质量真机演示的综合成本在几十元到上百元人民币。百万级数据集意味着千万级投入。

**这是"上游数据平台"存在的全部理由**——不是存数据，是降低"从物理世界获取可用数据"的成本。

### ④ 跨本体不通用

CV 的 ImageNet 任何模型都能用。机器人数据不行：action 空间不同、传感器配置不同、动力学不同。

所以这个领域才拼命做 cross-embodiment——先统一动作表示（比如都转成末端执行器的增量位姿），才能合并数据。代价是丢失关节层面的细节。

### ⑤ 标注不是"打标签"，是"重看一遍"

图像分类的标注是给已有图片点个类目。机器人数据的标注要求人**回放整段轨迹**，判断任务是否成功、在哪一步失败、怎么切分子任务。

一段 30 秒数据的质量检查，可能就是 30 秒的人力。所以标注成本和数据量是线性关系，规模化的唯一出路是自动评估（在仿真里重放、用 VLM 判定、用成功检测器）。

## 4. 一段真实记录长什么样

抽象讲完，看具体的。

**rosbag2 录制（原始形态）**：

```
episode_0042/
├── metadata.yaml          # 记录所有 topic 的类型、频率、消息数
├── episode_0042_0.mcap    # 实际数据，按时间交错存储
```

`metadata.yaml` 大致长这样：

```yaml
rosbag2_bagfile_information:
  duration: {nanoseconds: 31400000000}      # 31.4 秒
  message_count: 12847
  topics_with_message_count:
    - topic_metadata: {name: /camera/wrist/color/image_raw, type: sensor_msgs/msg/Image}
      message_count: 942                     # ≈30 Hz
    - topic_metadata: {name: /joint_states, type: sensor_msgs/msg/JointState}
      message_count: 3140                    # ≈100 Hz
    - topic_metadata: {name: /ft_sensor/wrench, geometry_msgs/msg/WrenchStamped}
      message_count: 31400                   # ≈1000 Hz
```

注意 942 / 3140 / 31400 这三个数——它们不是整数倍关系，因为各传感器时钟独立。**这就是为什么必须做时间对齐，不能假设"每 33 条力矩对应 1 帧图像"**。

**训练用格式（LeRobotDataset 形态）**：

```
dataset/
├── meta/
│   ├── info.json                 # 全局 schema：特征定义、fps、总帧数
│   ├── episodes.jsonl            # 每个 episode 的任务、长度、索引
│   ├── episodes_stats.jsonl      # 每个 episode 的归一化统计量
│   └── tasks.jsonl               # 语言指令表
├── data/chunk-000/
│   └── episode_000042.parquet    # 对齐后的帧级数据（状态 + 动作 + 时间戳）
└── videos/chunk-000/
    └── observation.images.wrist/
        └── episode_000042.mp4    # 视频单独存，parquet 里存帧索引
```

注意几个设计决策，每一个都在解决上面提到的某个问题：

- **图像不存进 Parquet**，单独编码成 MP4，Parquet 里只存帧号 → 解决存储成本
- **`episodes_stats.jsonl` 存归一化统计** → 因为动作量纲随本体变化，不归一化没法训
- **所有模态在 Parquet 里已经是同一时间基** → 对齐工作前置到转换阶段，训练时不再处理

## 5. 和数据平台有什么关系

读完这篇，做平台的人该记住四件事：

1. **数据规模的主变量是"对齐后的帧数"，不是文件大小**。1 小时视频可能只有 10 分钟有效演示——中间全是重置和空转。
2. **元数据不是附属品，是数据的一部分**。标定信息缺失的数据集，价值直接归零。平台必须把元数据当一等公民，且做完整性校验（缺外参就拒绝入库）。
3. **"采集"和"标注"是同一个成本项**。别把流水线设计成"先采集完再统一标注"，成本会翻倍。
4. **跨本体是产品问题，不是格式问题**。平台如果只做格式转换（rosbag → Parquet），价值有限；真正的价值在**语义层的统一**（统一动作表示、统一任务描述、统一成功判定）。
