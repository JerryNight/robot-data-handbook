## 1. 它解决什么问题

机器人领域的新名词密度极高，而且大多没有中文共识译法。生啃定义的结果是：每个词都查了，合起来还是不懂它在系统里扮演什么角色。

如果你有软件/数据背景，最快的路径是**先建立映射，再修正映射**：先把新概念挂到已知概念上跑起来，然后在实践中发现"哦这里不一样"，认知就落地了。

这篇就是这个映射表。但请注意第 4 节的**边界警告**——类比用错方向，会把你带进更深的设计坑。

## 2. 映射表

### 2.1 系统与中间件

| 机器人概念 | 软件工程对应物 | 相同点 | 关键差异 |
|---|---|---|---|
| **ROS 2** | 分布式消息中间件（Kafka / NATS）+ 服务发现 | 发布订阅、多进程解耦、节点自动发现 | 无中心 broker（DDS 点对点）；有硬实时要求；消息类型是编译期确定的 |
| **Topic** | Kafka topic | 一对多广播、按名字路由 | 默认不持久化，消费者没在线就永远错过 |
| **QoS** | 消息队列的投递保证等级 | 可靠性 vs 延迟的取舍 | 配错**不会报错**，只会静默丢数据 |
| **Service / Action** | RPC / 带进度回调的异步任务 | 请求-响应、可取消 | Action 有中间反馈，像长任务的进度流 |
| **Node** | 一个微服务实例 | 独立进程、独立部署 | 生命周期常由 launch 文件统一编排 |
| **Launch File** | docker-compose.yml | 声明式拉起多个服务、配置参数 | 还负责节点启动顺序和时间同步配置 |

### 2.2 数据与格式

| 机器人概念 | 软件工程对应物 | 相同点 | 关键差异 |
|---|---|---|---|
| **URDF** | OpenAPI / Protobuf Schema | 声明式定义结构、被工具消费 | 定义的是**物理结构**（连杆、关节、惯量），不是数据字段 |
| **TF2** | 带时间维度的版本控制 + 配置中心 | 维护"某对象在某时刻的状态" | 只能是一棵树（无环），且查询必须带时间戳 |
| **rosbag2 / MCAP** | 事件溯源日志（WAL）+ 可回放 | 按时间顺序记一切，可重放 | 老 bag 格式没有索引，无法查询；MCAP 才有索引能力 |
| **LeRobotDataset** | 数仓里的一张宽表 + 对象存储里的媒体文件 | Schema 显式声明、媒体分离存储 | 天然带 episode 维度，不是扁平的行 |
| **episode** | 一次完整事务 / 一条 trace | 有开始、结束、结果 | 长度可变、成功率是关键元数据 |
| **HDF5** | 层级式文件系统打包成单文件 | 目录树结构、分块读取 | 并发写几乎不可用，不适合流式追加 |

### 2.3 概念与抽象

| 机器人概念 | 软件工程对应物 | 相同点 | 关键差异 |
|---|---|---|---|
| **Action space** | API 契约 / 函数签名 | 定义"能做什么、参数含义" | 不同本体签名不兼容，且**没有版本协商机制** |
| **State vector** | 服务的心跳指标快照 | 一维数组、有物理含义 | 维度随硬件配置变化，不存在统一的"标准状态" |
| **Observation** | 请求 payload | 模型/策略的输入 | 多模态、多频率，需要对齐 |
| **Policy** | 推理服务 | 输入 → 输出、可批处理 | **它是闭环的一部分**，输入分布随自己输出而变 |
| **Calibration** | 环境配置基线 / 时钟同步 | 一次配置、全局生效 | 会随时间漂移，需要定期重标 |
| **Sim2Real gap** | staging 与 prod 的差异 | 环境不一致导致行为异常 | 差异是连续的、无法完全消除，只能缩小 |

### 2.4 学习与数据工程

| 机器人概念 | 软件工程对应物 | 相同点 | 关键差异 |
|---|---|---|---|
| **Behavior Cloning** | 监督学习 / 日志回放训练 | 从历史数据学映射 | 部署后自己产生的分布会偏离训练集 |
| **Covariate shift** | training-serving skew | 训练分布与服务分布不一致 | 机器人里是**自我放大**的：错一步就进入更陌生的状态 |
| **Domain randomization** | 数据增强 + 混沌工程 | 主动引入扰动提升鲁棒性 | 随机化范围需要"刚好覆盖真实差异"，过大会学不出有效策略 |
| **Dataset versioning** | git for data（DVC / LakeFS） | 数据可追溯、可回滚 | 机器人数据集常有 TB 级，且版本间差异是"重采"不是"改文件" |
| **Data lineage** | 调用链追踪 | 一条数据从哪来到哪去 | 要追溯到**物理采集条件**（谁采的、什么场景） |
| **标注** | 人工审核 / 数据打标 | 人力密集、质量参差 | 需要回放整段轨迹，不是看一眼就能标 |

## 3. 三个最有用的类比（重点展开）

### 3.1 Action space ≈ API 契约，但没有版本管理

这是理解"为什么跨本体数据不能混用"最快的路径。

想象你有两个微服务：一个的 `createOrder(amount: int)` 单位是分，另一个是元。你不可能把它们的日志合并训练一个模型——语义冲突。

机器人一模一样：A 机器人的 action[6] 是"夹爪开合 0–1"，B 机器人的 action[6] 是"第 7 个关节角度（弧度）"。**两个 7 维向量，字面一样，语义完全无关。**

而软件世界有 OpenAPI、有 protobuf 的字段编号、有版本协商；机器人世界**什么都没有**。所以跨本体复用的唯一出路是人为定义一个"公共契约"（比如都转成末端执行器的增量位姿），代价是丢失本体特有的信息。

### 3.2 Policy ≈ 推理服务，但它是闭环的

普通推理服务：请求进来 → 输出结果 → 完事。input 分布由外部世界决定，服务自己不影响它。

策略不是。策略输出动作 → 机器人动 → 世界变化 → 下一帧观测改变。**策略的输出直接决定了它下一次的输入。**

这带来两个软件工程里没有的后果：

1. **离线指标不可信**。验证集 loss 很低，不等于真机能跑——因为验证集是"人操作产生的状态分布"，部署后策略会走进人没去过的状态。
2. **错误会累积**。一次小偏差导致状态偏移，偏移导致更大偏差，几步后彻底跑飞。这就是 DAgger 这类方法存在的原因：让策略自己跑，人来纠正它犯的错。

### 3.3 TF2 ≈ 带时间轴的坐标系版本控制

假设你要问："在 t=12.3 秒时，相机看到的那个杯子，在机器人基座坐标系下的位置是？"

需要知道：相机 → 腕部 → 基座 这一条链上每个变换在 t=12.3 秒时的值。**每个变换都是随时间变化的**（因为机器人在动）。

TF2 就是维护这棵树的系统：每个 link 之间的变换带时间戳存储，查询时必须指定时刻，它会插值。

类比 git：git 维护"文件内容随时间的变化"，TF2 维护"坐标系关系随时间的变化"。区别是 TF2 只能是一棵树（无环），且必须能插值（所以要求变换是连续的）。

**这是数据对齐的地基。** 标定给的是"静态外参"，TF 给的是"动态变换"，两者叠加才能把像素反投影到世界坐标。

## 4. 五个会害死你的错误类比

类比的价值在于入门，危险在于拿它做设计决策。以下五个必须警惕：

### ❌ "ROS 2 是机器人操作系统"

名字里有 OS，但它不是内核，不管理内存和进程调度。它只是一个通信中间件 + 工具集。真正的实时控制在驱动层（L1）和 RT 内核里，跟 ROS 2 关系不大。

**误判后果**：以为上了 ROS 2 就有实时性保证。实际 DDS 的默认配置在普通 Linux 上抖动可达几十毫秒。

### ❌ "rosbag 就是一个数据库，可以查询"

老 rosbag 格式是**纯顺序日志**，没有索引，想找"所有夹爪闭合的时刻"只能全量扫一遍。MCAP 加了索引能力，但依然不是数据库——没有 schema 约束、没有事务、没有并发写。

**误判后果**：设计平台时假设"直接在 bag 上跑 SQL"，最后发现必须全量转存一遍。

### ❌ "Policy 是个无状态函数"

它是闭环系统里的一个环节。同一个观测，在不同历史下应该给出不同动作（否则无法纠错）。很多 BC 模型恰恰学成了无状态映射，这是它们鲁棒性差的根源。

**误判后果**：只做单帧输入、不喂历史，然后困惑为什么模型不纠错。

### ❌ "数据越多越好"

机器人数据的边际收益衰减极快。10 万条在同一场景、同一光照、同一物体位置下的演示，不如 1 万条覆盖 20 种场景的。

**误判后果**：把预算全花在"多采"，而不是"采得多样"。

### ❌ "仿真里能跑通，真机就差一点"

差的不止一点。仿真没有摩擦模型误差、没有相机噪声、没有通信延迟、没有机械回差。Sim2real 的差距是**结构性**的，不是调调参能解决的。

**误判后果**：把仿真成功率当项目进度指标。

## 5. 和数据平台有什么关系

三个实际影响：

1. **用"契约"的思维设计数据 Schema。** 你要处理的核心矛盾不是"怎么存"，而是"不同本体的 action/state 怎么映射到统一语义"。这件事在软件世界有成熟解法（中间表示 + 适配层），可以直接借鉴。
2. **把"数据质量"当成 SLO 来管。** 缺帧率、时间戳抖动、标定缺失率——这些应该像服务的错误率一样被监控和告警，而不是靠人工抽查。
3. **不要用 OLTP 的直觉设计存储。** 机器人数据的访问模式是"整段读、顺序写、按 episode 检索"，接近视频点播而不是订单系统。列式 + 对象存储 + 索引分离更合适。
